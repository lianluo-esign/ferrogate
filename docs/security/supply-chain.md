# Container Image Supply-Chain Verification

FerroGate publishes container images to GHCR through one release-gated chain:

- `.github/workflows/ci-image.yml` builds the commit-addressed image after
  `rust-ci` passes, then signs and attests its immutable digest.
- `.github/workflows/package.yml` is `workflow_call`-only. It verifies that
  exact digest and source revision, then promotes the digest to
  `vYYYY.MM.DD`, `stable`, and `latest`. It never rebuilds or signs a different
  image.

The immutable build step produces five artifacts with the shared
`.github/actions/image-supply-chain` composite action before package promotion:

1. An SPDX-JSON **SBOM** of the built image, uploaded as a GitHub Actions
   workflow artifact.
2. A **cosign keyless signature** over the image digest.
3. A GitHub **build provenance attestation** for the image digest, pushed to
   the registry alongside the image.
4. A signed **SPDX-JSON attestation** whose subject is the same immutable image
   digest, so an operator can verify SBOM association without trusting a
   workflow-artifact filename.
5. A signed **build-input attestation** containing the repository, workflow
   ref, commit SHA, image digest, and SHA-256 values for `Cargo.lock` and the
   `Dockerfile`.

This page documents how to check all five artifacts against
`ghcr.io/lianluo-esign/ferrogate`.

All external actions used by the release gate and shared action are pinned to
full commit SHAs. `scripts/check-workflow-action-pins.py` enforces that policy;
version comments remain only as human-readable upgrade context.

## Why keyless OIDC signing, not a stored key

Signing uses `cosign sign` with GitHub Actions' OIDC identity (`id-token:
write` permission, [sigstore/cosign-installer](https://github.com/sigstore/cosign-installer)
+ Fulcio + Rekor) instead of a long-lived cosign key pair stored as a repo
secret. A stored private key is a standing secret that has to be rotated,
can leak from a compromised runner or misconfigured log, and — critically —
its compromise is silent: nothing forces re-authentication per build. Keyless
signing binds each signature to the specific GitHub Actions workflow run that
produced it (recorded in the Fulcio short-lived certificate and the public
Rekor transparency log), so there is no persistent secret to steal and every
signature is independently auditable against the workflow identity that
created it. This is also what issue #189's acceptance criteria requires: "No
new long-lived signing secrets are introduced."

## What the SBOM covers

The SBOM is generated by [`anchore/sbom-action`](https://github.com/anchore/sbom-action)
(Syft under the hood) scanning the **built and pushed image**, not the
source tree — it inventories what actually ships: the base image's OS
packages plus anything installed into the final image layers. It does not
separately enumerate FerroGate's Rust/Cargo build-time dependency graph;
`cargo-deny`/`cargo-audit` (`.github/workflows/rust-quality.yml`) already
cover that as a source-level check per `Cargo.lock`. The two checks are
complementary, not duplicates: one covers what's compiled in, the other
covers what's in the shipped artifact.

The workflow artifact is named `sbom-ci-image-<short-sha>.spdx.json`; the
signed SPDX attestation is associated with the digest and remains authoritative
after that digest is promoted to release tags.

## Consumer verification

Use the repository verifier instead of reconstructing identity flags by hand:

```bash
scripts/verify-image-supply-chain.sh \
  --mode release \
  --image ghcr.io/lianluo-esign/ferrogate@sha256:<64-lowercase-hex> \
  --workflow-ref refs/tags/v2026.07.12 \
  --source-digest <40-character-commit-sha>
```

The consumer needs `cosign` v3, GitHub CLI with `gh attestation verify`, and
Python 3.11 or newer. Private-package consumers must authenticate to GHCR;
verification never requires a repository signing secret.

Pass the workflow ref shown by the release attestation. The script rejects
tags, non-FerroGate repositories, abbreviated digests, unexpected workflow
paths, and malformed source revisions before invoking verification tools. The
verifier checkout must be at the exact source commit; it computes the committed
`Cargo.lock` and `Dockerfile` hashes and compares them with the signed predicate.
It then verifies the image signature, SPDX SBOM attestation, FerroGate
build-input attestation, and GitHub SLSA provenance. Both modes pin the signer
to `ci-image.yml`, because `package.yml` only promotes the already verified
digest and never creates a second signing identity.

The underlying signature check is equivalent to:

Verify the image digest was signed by this repository's GitHub Actions
identity:

```bash
cosign verify \
  --certificate-identity 'https://github.com/lianluo-esign/ferrogate/.github/workflows/ci-image.yml@refs/tags/v2026.07.12' \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  ghcr.io/lianluo-esign/ferrogate@<digest>
```

Replace `<digest>` with the `sha256:...` digest of the tag you care about,
e.g. `docker buildx imagetools inspect ghcr.io/lianluo-esign/ferrogate:stable
--format '{{json .Manifest.Digest}}'`, or read it directly from the `Build
and publish image` step's output in the workflow run.

A successful verification prints the signing certificate's claims and exits
0; an unsigned or tampered image prints `Error: no matching signatures` and
exits non-zero.

Because the CI-image path runs through a reusable workflow, Fulcio records
`ci-image.yml` as the signer, not the calling `ci.yml`. The verifier requires
the exact expected workflow path and ref; accepting every workflow in the
repository would let an unrelated workflow satisfy the trust policy.

The SBOM association is separately checked with `cosign
verify-attestation --type spdxjson`. Build inputs use predicate type
`https://token4ai.cloud/ferrogate/build-inputs/v1`. Both attestations are
keyless-signed and attached to the immutable image digest in GHCR.

## Verifying the build provenance attestation

```bash
gh attestation verify oci://ghcr.io/lianluo-esign/ferrogate@<digest> \
  --repo lianluo-esign/ferrogate
```

This checks the artifact against GitHub's attestation API for the
`lianluo-esign/ferrogate` repository and validates the SLSA provenance
predicate (`https://slsa.dev/provenance/v1`) by default. Requires `gh` with
the `attestation` command (bundled since GitHub CLI 2.49+) and that you are
authenticated to pull from `ghcr.io` (`docker login ghcr.io` /
`gh auth token | docker login ghcr.io -u USERNAME --password-stdin`) before
running an `oci://` verification, since `gh attestation verify` needs
registry access to fetch the image manifest.

## Failure, rotation, revocation, and exceptions

- **Publish failure:** SBOM generation, signing, either cosign attestation,
  GitHub provenance, or pre-promotion verification failure prevents
  `vYYYY.MM.DD`, `stable`, and `latest` from being created or moved. The
  immutable `sha-<commit>` staging digest may remain as failure evidence.
- **Workflow identity rotation:** moving or renaming a signing workflow is a
  trust-root change. Update the verifier and this document in an issue-linked,
  reviewed commit before publishing with the new identity. Do not broaden the
  certificate regexp to make rotation convenient.
- **Action dependency rotation:** update an external action only by resolving
  its reviewed release tag to a full commit SHA, changing the version comment,
  and running the immutable-reference policy test. Moving major-version tags
  are not accepted in release workflows.
- **OIDC/Sigstore rotation:** keyless signing has no repository private key.
  Changes to the GitHub OIDC issuer, Fulcio, Rekor, or trusted root require a
  recorded verification run and verifier update before the next release.
- **Incident revocation:** remove mutable tags from a compromised digest,
  mark the GitHub Release as withdrawn, publish a security advisory naming the
  digest, and publish a newly built digest. Signatures are immutable evidence;
  deleting or hiding them is not a substitute for recording the incident.
- **Vulnerability exceptions:** every `.cargo/audit.toml` ignore must have an
  owner, expiry, tracking issue, and risk rationale in
  `.cargo/audit-exceptions.json`. `scripts/check-audit-exceptions.py` fails
  local and release quality gates for missing, stale, duplicate, expired, or
  longer-than-90-day exceptions. Extension requires a new dated review; an
  expired exception blocks release.

## Local verifier evidence for #208

- `cosign verify` command syntax, flags, and the full Fulcio/Rekor
  verification round-trip were exercised locally against a real, publicly
  keyless-signed GHCR image (`ghcr.io/goreleaser/goreleaser:latest`, signed
  via GitHub Actions OIDC) using cosign v3.1.1, and it passed:
  the command printed a valid signature verification with claims validated
  against the transparency log. This confirms the command shape documented
  above is correct cosign usage. It does **not** confirm that FerroGate's new
  signed SPDX and build-input predicates have been published successfully.
- `gh attestation verify --help` confirms the `oci://`, exact
  `--cert-identity`, `--cert-oidc-issuer`, `--repo`, and `--source-digest`
  controls used by the verifier exist in the installed `gh` 2.96.0.
- `anchore/sbom-action`, `sigstore/cosign-installer`, and
  `actions/attest-build-provenance` version tags used in the workflows
  (`v0.24.0`, `v4.1.2`, `v3` respectively) were confirmed to exist via the
  GitHub API and their published READMEs at those refs; the
  `attest-build-provenance` step mirrors that action's own documented
  container-image example (`subject-name` + `subject-digest` +
  `push-to-registry: true`).
- `scripts/test-verify-image-supply-chain.sh` uses controlled `cosign` and
  `gh` doubles to prove the verifier passes the exact trusted identity and
  predicate type, rejects a mutable tag and wrong repository, rejects a
  mismatched signed build-input predicate, and propagates cryptographic
  verification failure.
- `scripts/test_audit_exceptions.py` proves valid, expired/ownerless, missing,
  and stale advisory exception cases. The release quality gate runs both test
  contracts and `scripts/security-check.sh` enforces the live exception file.
- `scripts/test_workflow_action_pins.py` proves commit-pinned and local actions
  pass while a movable version tag fails. The same checker scans every release
  workflow and composite action in the quality gate.
- The updated workflow and composite-action YAML parse locally. The signed
  SPDX and build-input attestation steps have **not** yet run on a published
  FerroGate digest; only a real release can provide that evidence.

## Real end-to-end verification (2026-07-09, closes issue #189)

Before CI became release-only, `ci.yml` was dispatched once against `main` at
commit `18f81b4` specifically
to exercise this pipeline for real (`gh workflow run ci.yml --ref main`, run
[29004136692](https://github.com/lianluo-esign/ferrogate/actions/runs/29004136692)).
This publishes only `sha-<commit>` tags via `ci-image.yml` — it does not
touch `package.yml`'s `:stable`/`:latest` release tags. The first attempt's
`rust-e2e-harness` job failed on an unrelated transient Docker Hub registry
500 pulling `postgres:16-alpine`; `gh run rerun --failed` re-ran only that
job and it passed on retry, confirming the failure was infra flake, not a
regression from the MySQL removal or CI trigger changes landed in this same
session.

Resulting image: `ghcr.io/lianluo-esign/ferrogate@sha256:7329e4872d48b68b975437515538b36a149564e33d468baf1a7ef32f449750b7`
(tags `sha-18f81b4fba9fe06761bc09f035f806cb907a5d4d`, `sha-18f81b4fba9f`).

Both verification commands above were run against this real digest, not a
hypothetical one:

- `cosign verify --certificate-identity-regexp '^https://github.com/lianluo-esign/ferrogate/\.github/workflows/.*$' --certificate-oidc-issuer https://token.actions.githubusercontent.com ghcr.io/lianluo-esign/ferrogate@sha256:7329e48...` —
  **passed**. Printed two verified claims: a `sigstore.dev/cosign/sign/v1`
  signature and a `slsa.dev/provenance/v1` attestation, both binding
  `docker-manifest-digest` to the exact digest above, both checked against
  the transparency log offline and validated against the Sigstore root CA.
- `gh attestation verify oci://ghcr.io/lianluo-esign/ferrogate@sha256:7329e48... --repo lianluo-esign/ferrogate` —
  **passed** (exit 0). `--format json` returned one attestation record whose
  embedded Fulcio certificate SAN identifies the signer as
  `https://github.com/lianluo-esign/ferrogate/.github/workflows/ci-image.yml@refs/heads/main`
  triggered by `workflow_dispatch` at commit `18f81b4fba9fe06761bc09f035f806cb907a5d4d`
  — an independently auditable, cryptographic link from the published image
  back to the exact workflow file and commit that built it.

This closes issue #189's remaining acceptance item: a real image was
published with SBOM + signature + attestation, and both verification
commands were run end-to-end against its actual digest with the results
recorded here.

That 2026-07-09 digest predates the signed SPDX and build-input attestations
added for #208. It remains valid evidence for the image signature and SLSA
provenance, but it is not evidence that the two new predicate types publish
successfully. #208 must remain open until the next release-produced digest is
verified in a clean consumer environment, including negative checks for a
tampered digest, wrong workflow identity, and an unsigned image.
