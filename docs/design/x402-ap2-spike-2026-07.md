## 1. What the protocols actually say (primary sources read)

### 1.1 x402 — HTTP-native micropayment protocol

Source: [x402-foundation/x402](https://github.com/x402-foundation/x402),
specifically `specs/x402-specification-v2.md` (fetched via `gh api
repos/x402-foundation/x402/contents/specs/x402-specification-v2.md`, 740
lines, Protocol Version 2) and [docs.x402.org/core-concepts/http-402](https://docs.x402.org/core-concepts/http-402).
Note: the protocol originated at `coinbase/x402` and was later handed to the
`x402-foundation` org as the canonical spec home; both repos exist, foundation
is current.

**Three components** (spec §3): **Resource Server** (requires payment for a
protected resource), **Client** (any application/agent requesting the
resource), **Facilitator** (a third-party service that handles payment
*verification* and *blockchain settlement* on the resource server's behalf —
the resource server may also do both itself).

**Core flow** (spec §2, and confirmed against docs.x402.org's V2 header
model):

1. Client makes a normal HTTP request to a resource server.
2. No valid payment attached → server responds `402 Payment Required` with a
   base64-encoded `PaymentRequired` JSON object in the `PAYMENT-REQUIRED`
   response header. It contains `x402Version`, an `accepts` array of
   `PaymentRequirements` (`scheme`, e.g. `"exact"`; `network` as a CAIP-2 id,
   e.g. `"eip155:84532"`; `amount` in atomic token units; `asset` — a token
   contract address or ISO-4217 code; `payTo` — recipient wallet address;
   `maxTimeoutSeconds`), plus a `resource` descriptor (url, mimeType,
   serviceName) and optional `extensions`.
3. Client picks one `PaymentRequirements` entry, constructs a
   `PaymentPayload` (its own `payload` field is scheme-specific — for the
   `exact` EVM scheme this is an EIP-712 `signature` plus an EIP-3009
   `authorization` object: `from`, `to`, `value`, `validAfter`,
   `validBefore`, `nonce`), base64-encodes it, and retries the request with
   the `PAYMENT-SIGNATURE` header set.
4. The resource server verifies the payload — either locally, or by POSTing
   `{x402Version, paymentPayload, paymentRequirements}` to a facilitator's
   `POST /verify` endpoint, which returns `{isValid, payer}` or
   `{isValid: false, invalidReason, payer}` (spec §7.1). **Verification does
   not move funds** — it checks the signature/authorization is well-formed
   and (implementation-dependent) that the payer has sufficient balance.
5. If valid, the resource server does the work, then settles — either
   directly on-chain, or via the facilitator's `POST /settle` (same request
   shape as `/verify`; spec §7.2), which broadcasts the transaction, waits
   for confirmation, and returns a `SettlementResponse`
   (`success`, `transaction` hash, `network`, `payer`, optional `amount`).
6. Server returns `200 OK` plus a `PAYMENT-RESPONSE` header carrying the
   base64-encoded `SettlementResponse`.

**Trust model** (explicit design principle, spec intro + FAQ): "no payment
scheme should allow a facilitator or resource server to move funds outside of
client intentions." The client signs an *authorization* (EIP-3009
`transferWithAuthorization` for the `exact` EVM scheme), not a blank check —
the facilitator can only execute what that signature already permits, up to
the signed `value`/`validBefore` bounds. This is the load-bearing property for
§3 below: a facilitator is not a custodian in the traditional sense, it is a
relay+verifier for a client-signed, bounded, single-use authorization.

### 1.2 AP2 — Agent Payments Protocol (mandate layer, payment-agnostic)

Sources: [google-agentic-commerce/AP2](https://github.com/google-agentic-commerce/AP2)
(README — repo layout only, no deep spec content is in the README itself),
[ap2-protocol.org/topics/core-concepts](https://ap2-protocol.org/topics/core-concepts/)
(fetched successfully), and secondary corroboration via web search of
[ap2-protocol.org/topics/ap2-and-x402](https://ap2-protocol.org/topics/ap2-and-x402/)
(direct fetch 404'd through the WebFetch tool; content below is reconstructed
from search-result excerpts of that exact page plus the Google Cloud
announcement blog and Crossmint's protocol comparison — flagged as
secondary-sourced, not directly fetched).

AP2 solves a different problem than x402: not "how does money move" but "how
do we get cryptographic proof the user actually authorized what the agent
did." Three **mandates**, each a tamper-evident signed **Verifiable Digital
Credential**:

- **Intent Mandate** — user's upfront authorization of what the agent may do
  (constraints: price limits, timing, scope). Open (pre-cart) or Closed
  (bound to a finalized checkout) variant.
- **Cart Mandate** — merchant-generated, user-signed, binds identity +
  payment method token + exact transaction details (products, amount,
  currency) for a human-present purchase.
- **Payment Mandate** — authorizes a specific payment instrument for the
  transaction; shared with the Credential Provider, card networks, and
  Merchant Payment Processor.

AP2 has **no transport of its own** — it rides on **A2A** (Agent-to-Agent
protocol), advertised via `capabilities.extensions` on a participant's A2A
Agent Card. For crypto rails specifically, a **sibling extension, `a2a-x402`**,
bridges AP2 mandates to x402 settlement: the user signs a Cart Mandate, the
merchant's payment endpoint returns HTTP 402 with x402 payment terms, the
client signs the x402 EIP-3009 authorization *referencing* the upstream
mandate, and the facilitator settles on-chain. Two independent signatures
stack: the AP2 mandate attests *authorization intent*, the x402 signature
attests *payment movement* — different claims, verified independently.

**Implication for FerroGate**: x402 is the wire-level payment mechanism; AP2
is an optional higher-level consent/audit layer on top of it, carried over
A2A. FerroGate today speaks neither A2A nor AP2's mandate format — the
narrow scenario in §3 is x402-only (a bare HTTP 402 challenge on an egress
call), because that is the smallest unit FerroGate could plausibly intercept
without first building A2A support. AP2 becomes relevant only if FerroGate
later wants to *originate or verify mandates itself* rather than just
authorize the underlying x402 spend — out of scope for this spike (see §5).

## 2. FerroGate's actual billing/policy boundary today

All references verified against the working tree at the time of writing
(commit range ending `9882c73`).

### 2.1 Wallet: `StoredWallet` (issue #169)

`crates/ferrogate-storage/src/wallet.rs:26-50` — one prepaid-credit wallet
per tenant (`id == tenant_id`), opt-in (no row ⇒ no enforcement). Fields:
`balance_credits: i64` (integer credits, not floating USD — avoids rounding
drift), `auto_recharge_threshold_credits` / `auto_recharge_amount_credits`,
`dunning: bool`.

Balance mutation is a **direct atomic delta**, not a reserve/hold:
`adjust_wallet_balance(tenant_id, delta_credits, now)` issues a single
`UPDATE wallets SET balance_credits = balance_credits + $1 ...`
(`crates/ferrogate-storage/src/wallet.rs:172` Postgres path, `:285` in-memory
path). There is **no two-phase reserve/commit anywhere in the wallet code** —
confirmed by reading `state_wallets.rs` and `auth.rs` in full.

### 2.2 Pre-flight authorization gate

`AppState::wallet_balance_exhausted` (`crates/ferrogate-gateway/src/state_wallets.rs:129`)
checks `balance_credits <= 0`. It is invoked from `finalize_auth`
(`crates/ferrogate-gateway/src/auth.rs:434`, gate at `:482-495`) **before** an
LLM call is dispatched, returning HTTP 429 `wallet_balance_exhausted` if the
wallet is already empty. This runs immediately after the existing
`monthly_budget_exceeded` throttle check (`auth.rs:457`).

This is **check-then-proceed**, not reserve-then-settle: nothing is held
against the balance at authorization time. The actual debit happens later,
post-hoc, once the real cost is known:
`AppState::debit_wallet_for_settled_cost` (`crates/ferrogate-gateway/src/state_wallets.rs:160`)
converts a settled `cost_usd` into negative credits and calls
`adjust_wallet_balance`, invoked from the metering path
(`state_billing_metering.rs`, `record_billing_token_usage` →
`debit_wallet_for_settled_cost` at `state_wallets.rs:84-86` relative call
site). Between authorization and settlement, concurrent requests can drive
the wallet negative — there is no lock/hold. FerroGate accepts this today for
LLM billing because token-usage cost variance is small and bounded; it is not
a general-purpose "authorize an exact, unknown-until-signed amount"
primitive.

### 2.3 Ledger / audit trail

Two separate logs, not one:

- **Billing ledger** — `LedgerEntry` (`crates/ferrogate-billing/src/ledger.rs:58-93`)
  is a real idempotent transaction record: `id` (idempotency key, format
  `ferrogate:{trace_id}:{request_id}` via `ledger_entry_id()` at
  `ledger.rs:97-104`), `cost: CostEstimate`, `credits: f64`,
  `occurred_at_unix`, and (issue #169) `wallet_delta_credits` /
  `wallet_balance_after_credits` mirrored through from the originating
  `BillingEvent`. Per the doc comment at `ledger.rs` (`CostSource` block,
  lines ~30-40) and `ferrogate-billing/src/lib.rs:174-189`, this crate
  **records** the wallet outcome but never computes or applies the mutation
  itself — that responsibility stays in `ferrogate-cli`.
- **Wallet ledger events** — not a dedicated table; derived by filtering the
  general admin audit-event log for `action.starts_with("wallet.")`
  (`state_wallets.rs:255-264`, populated via `record_wallet_ledger_event` at
  `:220-244`). These are action/outcome/message strings, no structured
  amount/idempotency-key columns of their own — idempotency for this side
  comes from the underlying `adjust_wallet_balance` UPDATE being safe to
  re-run and from the billing ledger's `LedgerEntry.id` on the other side.

### 2.4 Policy engine vs. spend authorization — two unconnected systems

`PolicyEngine::evaluate()` (`crates/ferrogate-policy/src/lib.rs:20-27`)
returns `Allow | Deny { code, message }` and is a pure model/provider
allow-deny rule matcher scoped by `PolicySubject { organization_id,
project_id, api_key_id }`. **It takes no cost or wallet input at all.** The
actual spend gate — `wallet_balance_exhausted` / `monthly_budget_exceeded` —
lives entirely in `ferrogate-cli/src/auth.rs`, not in `ferrogate-policy`.
Similarly, the RBAC system (`Permission -> Role -> TenantRoleBinding`,
`crates/ferrogate-storage/src/rbac.rs:23-83`, enforced via
`AppState::tenant_has_permission`) gates asset hosting and other capability
grants but **does not gate wallet spend** — wallet admin endpoints
(`crates/ferrogate-gateway/src/server/wallets.rs`) use the older capability-scope
`authenticate(..., "admin.read"/"admin.write", ...)` mechanism instead. These
are three separate, currently-unconnected authorization systems
(policy-engine, RBAC, wallet-balance-gate) that happen to all execute inside
the same request path.

### 2.5 Existing outbound-call interception point

`docs/design/function-egress-broker.md` describes — and
`crates/ferrogate-runtime/src/function_egress.rs` +
`crates/ferrogate-gateway/src/function_egress.rs` (294 lines) partially
implement — a gateway-mediated outbound call broker: agent → `POST
/v1/functions/execute` → gateway authenticates the caller, checks a
per-tenant allowlist (`FunctionEgressAllowlist`, fail-closed), mints a
short-lived JWT, and makes the outbound TLS call itself (via `reqwest`) so
the agent/worker never holds the destination credential. This is a genuine
precedent for "gateway intercepts and mediates an outbound HTTP call," but
per the doc's own status note, `auth_key_ref` is not yet resolved against a
tenant secret store (single-project only today), and **there is no HTTP
402/retry-with-payment handling anywhere in this or any other path** — that
logic does not exist in any form yet.

## 3. Walk-through: could FerroGate gate an x402 402-challenge against the existing wallet?

**Narrow scenario, and only this scenario:** an agent, acting through
FerroGate's function-egress broker path, calls an external API that is
x402-priced. The external API responds `402 Payment Required` with a
`PaymentRequirements` entry whose `scheme` FerroGate recognizes as one it is
willing to fund (e.g. a stablecoin `exact` payment under some ceiling) for
that tenant.

Mapping onto the existing code:

1. **Interception point** — the outbound call already happens *inside* the
   gateway process at `gateway/function_egress.rs`'s dispatch step, not on
   the agent/worker. A 402 response from the upstream is just another
   `reqwest::Response` status the broker already sees before returning to
   the caller. No new interception surface is needed — this is the one part
   of the walk-through that is genuinely *not* greenfield.
2. **Authorization decision** — this is where the analogy breaks down
   partially. FerroGate's existing gate (`wallet_balance_exhausted`,
   §2.2) answers "is the balance currently non-negative," evaluated
   *before* a cost is known and enforced with no hold. An x402
   `PaymentRequirements.amount` is a **known, exact, atomic-unit price
   quoted before the client commits** — structurally close to a real
   reserve/commit primitive, which FerroGate's wallet code does not have.
   Reusing `wallet_balance_exhausted` as-is would only be a s balance-may
   check ("is `balance_credits` currently ≥ the quoted amount"), not a
   reservation — a second concurrent 402 challenge against the same wallet
   could pass the same check before either debits, exactly the existing
   known gap in §2.2, but now against attacker-observable, exact-amount,
   irreversible spend instead of small LLM-token variance. **This is a
   real gap, not a hypothetical one** — it must be closed (see §4) before
   any funds-adjacent version of this ships, even in a narrow slice.
3. **Debiting the wallet** — `adjust_wallet_balance` (§2.1) already accepts
   an arbitrary signed credit delta; converting a quoted x402 `amount` (in
   whatever `asset` units) to FerroGate credits at authorization time and
   calling this function is mechanically identical to what
   `debit_wallet_for_settled_cost` already does for LLM billing
   (`state_wallets.rs:160`). No new storage primitive is required for this
   step alone.
4. **Audit trail** — `record_wallet_ledger_event` (§2.3) already exists for
   exactly this purpose and needs no schema change to record a
   `wallet.x402_payment_authorized` action alongside the existing
   `wallet.*` actions.
5. **What FerroGate does *not* need to become** — critically, nothing in
   steps 1-4 requires FerroGate to hold, sign, or move actual on-chain
   funds. The client-side signing (EIP-3009 `authorization` + EIP-712
   `signature`, spec §5.2) and settlement (facilitator `/settle`, spec
   §7.2) are properties of the **x402 payer's own wallet key** — which in
   this scenario would need to be a wallet FerroGate operates on the
   tenant's behalf (custodial) or a wallet the tenant's agent holds
   directly and FerroGate merely *authorizes the decision to spend from*
   (non-custodial, gateway-as-policy-decision-point). Section 4 explains
   why the second shape is the only one consistent with FerroGate's
   existing trust boundary, and why it is a much smaller scope than "agent
   payments" sounds.

## 4. Go / no-go

### Verdict: **GO — but narrowly scoped as "authorize + audit only," never custody.**

**Reasoning, stated plainly:**

FerroGate's existing wallet is *already* an internal, non-blockchain ledger
that answers "may this tenant spend N units against their prepaid balance,
and if so, record it" — which is structurally the same question x402's
authorization step asks, just for a different unit (credits vs. atomic
token amounts) and a different settlement rail (Postgres UPDATE vs. on-chain
broadcast). The x402 trust model is explicitly designed so a facilitator
"cannot unilaterally move funds, only execute what the client authorized"
(§1.1) — FerroGate can occupy that same role for its own tenants' internal
credit balance without ever touching the on-chain leg: FerroGate decides
*whether* a tenant's agent is allowed to let a payment proceed (by checking
and debiting the tenant's existing prepaid-credit wallet, exactly as it does
for LLM spend today) and records the decision, but the actual x402
`PaymentPayload` signature and settlement remain the tenant's own
wallet/key and the x402 facilitator's problem — never FerroGate's.

This keeps FerroGate on the correct side of the custodial line: it is not
holding stablecoins, not signing EIP-3009 authorizations, not talking to a
blockchain. It is doing exactly what it already does for token billing —
gating access to a downstream resource against an internal balance — one
layer removed from where the actual money moves. The alternative (FerroGate
signs/settles on the tenant's behalf) would require holding private keys or
integrating a custodial wallet provider, which is explicitly out of scope
per #191 and would turn FerroGate into a money-transmission-adjacent
business — a different company, not a spike.

**What must NOT be waved through**, because it's a real gap uncovered in
§3.2, not a hypothetical: the existing `wallet_balance_exhausted` +
`adjust_wallet_balance` pair is check-then-proceed with no hold. That is an
acceptable trade-off for LLM-cost variance (bounded, small, internal) but
**not acceptable for exact-amount, attacker-observable, irreversible x402
authorization decisions** — a real slice must add a reservation (hold N
credits, decrement on commit, release on expiry/`maxTimeoutSeconds`)
before any actual authorization decision is wired to real spend, even
credits-only. This is new code the wallet layer does not have today, and is
the single largest piece of net-new engineering this spike surfaces.

## 5. Smallest first E2E slice (if pursued)

Following `docs/dynamic-workflow.md`'s "define the E2E closure before
editing" convention — this is the next issue to file, not something this
spike implements:

- **Operator input**: an agent, via the existing `POST
  /v1/functions/execute` egress-broker path (`gateway/function_egress.rs`),
  calls an x402-priced target already on that tenant's
  `FunctionEgressAllowlist`.
- **Execution path**: broker dispatches the call; upstream responds `402`
  with a `PAYMENT-REQUIRED` header; broker parses `PaymentRequired.accepts`,
  selects a supported `scheme`/`network`/`asset` combination pre-configured
  for that tenant, converts the quoted `amount` to credits, calls a **new**
  `reserve_wallet_credits(tenant_id, credits, hold_id, expires_at)` (does not
  exist yet — the actual new primitive from §4) instead of
  `wallet_balance_exhausted`; on reservation success, returns a structured
  "payment authorized, here is the bounded spend receipt" response to the
  caller rather than attempting any on-chain signature itself — actual
  x402 `PaymentPayload` construction/signing stays entirely client-side
  (tenant's own agent/key), out of FerroGate.
- **Observable evidence**: a `wallet.x402_payment_authorized` audit event
  (via `record_wallet_ledger_event`) with the quoted amount, target
  resource URL, and hold id; wallet balance visibly decremented by the held
  amount in the admin wallet API; a rejected second concurrent request
  against an exhausted hold as proof the reservation actually closes the
  §3.2 race.
- **Focused test**: an integration test asserting that two concurrent
  authorization attempts against a wallet with exactly one unit of covering
  balance result in exactly one success and one `wallet_balance_exhausted`
  (or equivalent new `hold_conflict`) — the regression test that proves the
  gap identified in §3.2/§4 is actually closed, not just narrated.

This slice deliberately excludes AP2 mandates, any facilitator `/verify` or
`/settle` call, and any real signature construction — it proves only that
FerroGate's internal authorization+audit boundary can make the *decision*
correctly and safely under concurrency. Wiring an actual facilitator call
and a tenant-held signing key is a separate, later issue this spike does not
recommend committing to yet.
