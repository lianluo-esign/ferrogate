This document is the contract for operators and for anything scripting the
`ferrogate` CLI: which binaries a release publishes, and what may change about
the command surface between releases.

The full command surface itself lives in
[`docs/cli-reference.md`](./cli-reference.md), which is generated from the same
`clap` tree the binary parses. Migration notes from the legacy `admin-api`
naming live in [`docs/cli-migration.md`](./cli-migration.md).

## Supported targets

`released` targets are built, archived and checksummed by `scripts/package-cli.sh` as part of a release. `build-from-source` targets are expected to compile and pass tests, but the release process publishes no binary for them — install with `cargo install --path crates/ferrogate-cli` instead. A target is only `released` if something in this repository already builds it.

| Target triple | OS | Tier | Linkage | Archive | Why |
| --- | --- | --- | --- | --- | --- |
| `x86_64-unknown-linux-musl` | linux | released | static (musl, +crt-static) | `tar.gz` | already cross-compiled by scripts/build-image-crane.sh; static, so it carries no glibc baseline |
| `aarch64-unknown-linux-musl` | linux | released | static (musl, +crt-static) | `tar.gz` | already cross-compiled by scripts/build-image-crane.sh; static, so it carries no glibc baseline |
| `x86_64-unknown-linux-gnu` | linux | build-from-source | dynamic (glibc of the build host) | `tar.gz` | the container image builds this triple, but a published archive would inherit an undeclared glibc baseline; use the musl archive or build from source |
| `aarch64-unknown-linux-gnu` | linux | build-from-source | dynamic (glibc of the build host) | `tar.gz` | same undeclared glibc baseline as the x86_64 gnu triple |
| `aarch64-apple-darwin` | macos | build-from-source | dynamic (system libSystem) | `tar.gz` | no macOS build or notarization host in the release process; nothing signs or verifies a published binary |
| `x86_64-apple-darwin` | macos | build-from-source | dynamic (system libSystem) | `tar.gz` | no macOS build or notarization host in the release process; nothing signs or verifies a published binary |
| `x86_64-pc-windows-msvc` | windows | build-from-source | dynamic (MSVC CRT) | `zip` | no Windows build host in the release process; the MSVC toolchain cannot be driven from the Linux release path |

## Compatibility matrix

What each operator-visible surface promises within a release line, and what counts as a breaking change to it.

### Command names

- **Guarantee:** A command that has shipped keeps parsing. A rename adds the new name and keeps the old one as an alias that still performs the same action.
- **Breaking change:** Removing a command or an alias, or changing what an existing command path does.
- **Checked in:** docs/cli-reference.md (drift-checked against the assembled clap tree by the `reference_doc_is_in_sync` test)

### Flags

- **Guarantee:** An existing flag keeps its name, arity and meaning. New flags are optional and default to the previous behaviour.
- **Breaking change:** Removing a flag, making an optional flag required, or changing a default so an unchanged invocation behaves differently.
- **Checked in:** docs/cli-reference.md renders every flag of every command

### JSON output

- **Guarantee:** `--output json` is additive: fields may be added, and consumers must ignore unknown fields. Field names, types and nesting of already-emitted fields do not change.
- **Breaking change:** Removing or renaming a field, changing its type, or re-nesting it.
- **Checked in:** crates/ferrogate-cli/src/ctl/resource_cmd.rs and its `resource_cmd_test.rs` output-contract tests

### Exit codes

- **Guarantee:** The exit-code classes below are frozen: a given failure class keeps its numeric code, because scripts branch on it.
- **Breaking change:** Renumbering a class, or reclassifying a failure into a different class.
- **Checked in:** crates/ferrogate-control-plane-client/src/error.rs (`ExitClass::code`)

### Context schema

- **Guarantee:** `contexts.toml` is read forward- and backward-compatibly: every optional field is `#[serde(default)]`, so an older file loads in a newer CLI and a newer file loads in an older one with unknown keys ignored. The file never holds a token value, only how to obtain one.
- **Breaking change:** Adding a required field, changing the meaning of an existing field, or moving the file's default path.
- **Checked in:** crates/ferrogate-control-plane-client/src/context.rs and crates/ferrogate-cli/src/ctl/store.rs

### Control Plane API versions

- **Guarantee:** The CLI targets the Control Plane API surface declared in the checked-in OpenAPI document and tolerates unknown response fields. Coverage of that surface is enforced, not asserted: every public operation ID is either mapped to a command or carries a reviewed exclusion with an owner.
- **Breaking change:** An OpenAPI operation becoming unreachable from the CLI without a reviewed exclusion, or a duplicate command mapping.
- **Checked in:** crates/ferrogate-control-plane-client/src/parity.rs (`REVIEWED_EXCLUSIONS`, `build_report`)

## Exit codes

Frozen. Generated from `ExitClass` in `crates/ferrogate-control-plane-client/src/error.rs`, so a new class cannot reach the binary without appearing here.

| Code | Class | Meaning |
| --- | --- | --- |
| `0` | Success | The command completed and any mutation was accepted. |
| `2` | Usage | Caller-side misuse: bad flags, unknown command, or invalid local configuration/context. Nothing was sent. |
| `3` | Auth | Authentication or authorization failure: missing or invalid credential, insufficient scope, or wrong tenant. |
| `4` | NotFoundConflict | The addressed resource does not exist, or the mutation conflicts with current state. |
| `5` | Validation | The request reached the server and was rejected as invalid. |
| `6` | Transport | No authoritative server answer: connection failure, timeout, TLS failure, or a retryable throttle. Safe to retry only for reads or idempotent mutations. |
| `7` | Server | The server accepted the request but failed to process it. |

## Deprecation policy

A surface listed in the matrix above is never removed outright. It goes
through:

1. **Deprecate.** The replacement ships and the old form keeps working
   unchanged. Using the old form emits an actionable notice on **stderr**,
   never on stdout, so `--output json` stays machine-parseable and a piped
   consumer is unaffected. The deprecation is recorded in the table below and
   in `docs/cli-migration.md`.
2. **Migrate.** The deprecated form stays for at least one full calendar
   release line (`vYYYY.MM.DD` tags share a line while the year and month are
   unchanged). Documentation and examples move to the replacement immediately.
3. **Remove.** Removal happens only in a release whose notes name the removed
   surface and the replacement. Removing a command, a flag, a JSON field, an
   exit-code class or a context field without that notice is a defect, not a
   release decision.

Anything not listed in the matrix — log line wording, help text prose, the
ordering of human-readable (non-JSON) output — carries no stability promise and
may change in any release.
