# FerroGate release verification (consumer runbook)

This document describes exactly how a consumer verifies a FerroGate release
image, what evidence each step checks, the good/negative outcome matrix, and
the offline dry-run harness that proves the whole chain executable without a
public release. It makes no certification or audit claims beyond the evidence
produced by the commands below.

## Trust anchors (pinned)

| Anchor | Value |
| --- | --- |
| Image subject | `ghcr.io/lianluo-esign/ferrogate@sha256:<64 lowercase hex>` (immutable digest only; tags are never trusted) |
| Signing identity | `https://github.com/lianluo-esign/ferrogate/.github/workflows/ci-image.yml@refs/tags/vYYYY.MM.DD` (or an explicit `refs/heads/<branch>` for CI digests) |
| OIDC issuer | `https://token.actions.githubusercontent.com` |
| SBOM attestation type | `spdxjson` (SPDX 2.x JSON, generated by the anchore sbom-action step in `.github/actions/image-supply-chain`) |
| Build-input attestation type | `https://token4ai.cloud/ferrogate/build-inputs/v1` |
| Source binding | full 40-hex commit SHA; the verifier requires its own checkout HEAD to equal it |

## Consumer verification command

From a clean checkout of `lianluo-esign/ferrogate` at the exact release
commit (`git rev-parse HEAD` must equal the source digest), with `cosign` and
`gh` installed:

```bash
./scripts/verify-image-supply-chain.sh \
  --mode release \
  --image ghcr.io/lianluo-esign/ferrogate@sha256:<release digest> \
  --workflow-ref refs/tags/vYYYY.MM.DD \
  --source-digest <40-hex release commit sha>
```

Evidence checked, in order:

1. **Argument policy** — digest-pinned GHCR subject only, release-tag-shaped
   ref, full commit SHA, and checkout HEAD == `--source-digest`. The verifier
   then computes the `Cargo.lock` and `Dockerfile` SHA-256 from that exact
   commit (`git show <sha>:<file>`), not from the working tree.
2. **`cosign verify`** — keyless signature over the exact image digest, with
   `--certificate-identity` pinned to the `ci-image.yml` workflow at the
   release ref and `--certificate-oidc-issuer` pinned to GitHub Actions OIDC.
3. **`cosign verify-attestation --type spdxjson`** — a signed SPDX SBOM
   attestation exists for the same digest under the same identity/issuer
   (SBOM association).
4. **`cosign verify-attestation --type https://token4ai.cloud/ferrogate/build-inputs/v1`**
   piped into `scripts/verify-build-input-attestation.py`, which checks the
   signed predicate against the requested values: in-toto subject name +
   digest, repository, workflow ref, `commit_sha` == `--source-digest`, and
   `cargo_lock_sha256` / `dockerfile_sha256` equal to the digests computed
   from the verified source commit.
5. **`gh attestation verify oci://<image>`** — GitHub build provenance for the
   same digest, same identity/issuer, bound to the same source commit.

Any single failure aborts the whole verification (non-zero exit).

## Good + negative matrix

| Case | How it is exercised | Expected result |
| --- | --- | --- |
| good | correct digest, ref, source SHA against the signed bundle | PASS |
| tampered digest | same evidence, different `--image` digest | FAIL (no signature/attestation subject matches the digest) |
| wrong identity | `--workflow-ref` pointing at a forged ref → forged certificate identity | FAIL (certificate identity mismatch) |
| wrong issuer | evidence signed under a non-GitHub OIDC issuer | FAIL (certificate issuer mismatch) |
| unsigned | image/attestations present without signatures | FAIL (signature verification) |
| tampered attestation | signed build-input payload mutated after signing | FAIL (DSSE signature no longer verifies) |

## Offline dry-run harness (proven in-repo)

Because cutting a real release requires a maintainer tag push, the repo ships
an offline harness that proves the identical verifier logic end to end,
hermetically (no network, no Docker daemon, no registry):

```bash
./scripts/release-dryrun/run-matrix.sh
```

This runs in CI via `rust-quality.yml` alongside the verifier contract test.
What it does:

1. `scripts/release-dryrun/produce_bundle.py` computes a **deterministic
   stand-in image digest** bound to the exact Dockerfile build inputs of the
   checked-out commit (`sha256` over commit SHA + `Dockerfile` blob digest +
   `Cargo.lock` blob digest), generates an SPDX 2.3 SBOM from `Cargo.lock`,
   emits the build-input predicate with the exact field shape of
   `.github/actions/image-supply-chain`, and a SLSA v1 provenance statement —
   then signs the image payload and all DSSE attestation envelopes with an
   **ephemeral in-memory ECDSA P-256 key** that is discarded after signing.
2. `scripts/release-dryrun/run-matrix.sh` runs the **real**
   `scripts/verify-image-supply-chain.sh` (unmodified) against that bundle via
   `FERROGATE_COSIGN_BIN` / `FERROGATE_GH_BIN`, asserting PASS on the good
   bundle and FAIL on every negative case in the table above.

Shimmed vs real in the dry run:

* **Shimmed (clearly bounded):** the `cosign` / `gh attestation` CLI network
  surface (registry, Rekor, Fulcio). `scripts/release-dryrun/sigstore_shim.py`
  reads the local bundle instead, and the keyless Fulcio certificate is
  replaced by a signed "dry-run certificate" binding identity + issuer to
  each payload digest. The GHCR manifest digest is the deterministic stand-in
  described above. SBOM generation stands in for syft.
* **Real:** the consumer verifier itself (argument policy, source-commit
  binding, Cargo.lock/Dockerfile digest recomputation, predicate validation in
  `verify-build-input-attestation.py`), ECDSA P-256/SHA-256 signature
  verification of every payload (image signature, DSSE PAE for each
  attestation, and the identity binding), subject-digest matching, and
  identity/issuer matching.

## Remaining maintainer action (the one open step for issue #208)

Push a release tag `vYYYY.MM.DD` to `lianluo-esign/ferrogate`. That triggers
the gated release pipeline (`rust-ci` → `ci-image.yml` build → sign/attest →
exact-digest verification → `package.yml` promotion), producing a real GHCR
digest. Then, from a clean consumer environment with real `cosign` and `gh`,
run the same command as above against the published digest — plus the
tampered-digest / wrong-identity / unsigned negative checks — and record the
output on issue #208. No other code work is outstanding.
